# 实时日志跟随性能验证

修复重点是降低主线程排版和数据刷新开销。原版每次跟随刷新会读取末尾 1 MB，并在窗口移动后整体替换文本；每次界面更新还会重复设置 NSTextView 的文字和背景颜色，采样发现这些 setter 会触发大量排版。

现在保留增量解析状态，只读新增字节；NSTextStorage 按差量追加和分批淘汰，不重复设置未变化的外观属性，不为后台忙碌状态触发整个 SwiftUI 界面更新。实时活动窗口最多 256 KB，浏览历史仍可按需读取最多 1 MB，原始文件完整保存。后台刷新不转圈，显式导航等待超过 200 ms 才显示加载提示。

在本机 macOS 27 / Apple Silicon 上，以相同窗口配置、自动换行开启、约 20 MB 初始日志并持续追加约 20 KB/s 的合成负载对比。两版使用相同 QA 心跳探针，统计最近 200 次、间隔 50 ms 的主队列调度延迟。测量时日志任务仍在运行。

| 主线程调度延迟 | 原版 054fed0 | 优化后 |
| --- | ---: | ---: |
| P95 | 240.5 ms | 8.0 ms |
| 本窗口最大值 | 258.0 ms | 65.5 ms |
| 均值 | 43.7 ms | 1.9 ms |

这是本机合成负载的观测结果，不是帧率或所有硬件上的保证。原始汇总见 `performance/live-log-results.json`。

80 项测试通过，覆盖增量读取量、UTF-8 / ANSI 跨刷新边界、差量编辑与渲染窗口一致性、批次淘汰、巨量突发、文件截断和替换，以及运行结束后恢复较大的历史窗口。原生验证也确认了跟随期间持续更新、查看最早记录和恢复最新。

`LIVE_LOG_VALIDATION` 编译条件启用隔离 QA 窗口与有界心跳探针；必须使用临时 HOME、自建项目和合成命令。探针只写该 HOME 下的 `runbar-ui-latency.json`。常规测试和正式打包不启用这个条件，不包含探针或合成运行逻辑。
