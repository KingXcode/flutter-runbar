# 关联运行中的 Flutter App

项目与应用监听是两个独立来源，共用日志 / 网络查看区域。项目绑定源码目录并拥有启动的命令；应用监听绑定 App 身份，仅拥有与 VM Service 的连接，不拥有目标进程。

## 使用与状态

1. 侧栏底部选择「连接 App」，列表显示应用图标、名称及 PID。仅在用户选中某个应用后检查它的服务；刷新和搜索不会扫描全机端口。
2. 自动发现失败时展开地址输入框，粘贴完整的 DevTools 或 VM Service 链接，再连接。始终核对 `getVM.pid` 与选中进程，必要时通过 Flutter 服务能力进一步识别。
3. 连接后的顶部显示应用名、状态、DevTools 和「断开连接」，不显示源码目录与命令栏。日志及网络页可继续使用搜索、筛选、跟随和本地缓存。
4. 每次连接产生独立的监听记录。断开后可离线查看；再次连接或 App 重启会产生新记录，历史仍按应用归类。
5. 断开、退出 Runbar、App 退出及连接中断都会收尾本地记录。退出 Runbar 不会退出监听目标，也不根据历史 PID 自动连接、激活或终止进程。

侧栏保存的是 Bundle ID 与规范化的安装路径，不以 PID 作为永久身份；同 Bundle ID 的不同安装路径分别管理。重新添加已移除的应用时，能够复用历史中的相同应用身份。一个应用身份同时保留一个连接，避免重复采集。

## 发现与认证

- 候选列表包含普通前台 App，以及可识别的 Flutter 菜单栏 App。
- 自动连接优先使用本次 Runbar 运行中已经发现的完整 VM 地址，再检查所选 PID 的 TCP 监听端口；最多检查 8 个候选地址，单次 HTTP 返回上限 256 KiB。`lsof` 自身有超时与输出上限，不读取进程环境变量或整份系统日志。
- 常规开启认证的 VM 无法仅从端口推导认证路径。此时使用手动链接，不尝试猜测令牌、关闭认证或修改目标启动参数。
- 仅连接 loopback，保留认证路径，不跟随重定向。连接前后重新核对所选 App 的启动身份，防止 PID 回收后误关联。
- VM / DevTools 地址只保存在本次连接的内存状态，不写入应用配置或监听记录元数据。目标自行打印的内容仍会按正常日志规则保存。

## 日志、网络与 DevTools

日志使用 VM Service WebSocket 的 `Stdout`、`Stderr`、`Logging` 流，不截取另一个进程的终端管道。只接收订阅后的事件；某些流不受支持时提示实际能力，网络采集可独立工作。`developer.log` 的截断字符串会通过受限的 `getObject` 读取，超过 64K 字符仍提示截断，不声称拿到了原本不存在的历史日志。

单条 VM 事件上限 1 MiB；待落盘缓冲最多 64 KiB，约 100 ms 批量写入 `output.raw` 和接收时间索引。大块数据直接写盘；界面按既有窗口读取，不保留整份事件列表。写盘失败会结束监听并标注记录可能不完整。网络使用现有的摘要分页、正文缓存和容量限制，范围见 [网络采集说明](devtools-network-capture.md)。WebView、未接入 profiling 的原生网络库与 WebSocket 不因本功能自动获得支持。

DevTools 优先使用用户输入的完整本机页面链接；只有点击 DevTools 时才启动本机 SDK 的前端，复用「设置」中的额外 PATH。缺少 SDK 会明确提示。前端服务由 Runbar 自己拥有，正常退出时停止；与目标 App 的生命周期分开管理。

## 验证（2026-10-27）

- 真实 Dart VM 验证 stdout、stderr、中文 / Emoji、developer.log 长消息、完整落盘及断开后目标仍存活。
- 独立 Flutter 3.47.5 macOS Debug App 与隔离 HOME 的原生 Runbar：选择 App、认证地址输入、日志、请求列表和完整 JSON 响应缓存均验证；App 重启后 PID 改变，监听历史仍归入原应用。
- 手动断开和退出 Runbar 后，测试 App 的健康检查均继续成功；重启 Runbar 后能离线查看历史，不自动重连旧 PID。
- 本机 DevTools SDK 启停、启动地址末尾句号兼容、旧配置兼容、应用身份隔离和 PID 不匹配拒绝由专项测试覆盖。

验证仅使用独立测试程序，没有连接或修改业务 App。Debug / Profile 的实际扩展能力需要连接后检测，不能把 Flutter 框架存在或进程名视为保证可连接的依据。
