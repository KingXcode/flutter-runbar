# DevTools 网络请求采集可行性

结论：可实现独立的网络请求列表与本地缓存。适用对象是启用了 VM Service 和 HTTP profiling 的 Dart / Flutter 调试进程；不需要读取 DevTools 网页。现已接入 Runbar 的「日志 / 网络」面板，支持请求列表、详情、本地历史缓存与基本筛选。原型和正式 Swift 采集器均使用自建回环测试服务验证。

## 数据来源

DevTools Network 使用 Dart VM Service。可以从当前运行输出中的 DevTools URI 取得 VM Service 地址，查询 `getVM` / `getIsolate` 选择支持网络扩展的 isolate，再使用：

- `ext.dart.io.httpEnableTimelineLogging` 查询或开启记录。
- `ext.dart.io.getHttpProfile` 读取请求摘要；`updatedSince` 使用 Unix epoch 微秒，可增量查询更新。
- `ext.dart.io.getHttpProfileRequest` 按请求 ID 读取请求 / 响应正文。

摘要提供方法、URL、开始 / 完成时间、状态码及请求 / 响应信息；详细响应可带正文。完整耗时使用 `response.endTime`，顶层 `endTime` 只是请求发送结束，不能用于判断响应完成。正在接收的响应正文可能只有一部分，必须等响应结束后才能标为完整缓存。方法与字段来自 [Dart VM Service 扩展协议](https://github.com/dart-lang/sdk/blob/main/runtime/vm/service/service_extension.md) 和 [getHttpProfileRequest API](https://api.flutter.dev/flutter/vm_service/DartIOExtension/getHttpProfileRequest.html)。

## 支持范围

- `dart:io` HttpClient 流量，包括通过它发送的 Dio 请求，以及通过 `http_profile` 接入的客户端。可以显示 HTTP / HTTPS 请求；WebSocket / SOCKET 需要分别实现对应的 profiling 扩展，不能把 socket 统计当成完整 HTTP 报文。
- WebView、浏览器和没有接入 profiling 的原生网络库，不保证出现在这套接口中；Flutter Web 应使用浏览器的网络工具。
- 记录开启前未收集的请求无法追溯。如果要覆盖应用启动时的请求，应采用 `--start-paused` 等方式，在恢复运行前开启采集。
- Release / product 进程不应假定有可用的 VM Service，连接前必须检测实际扩展能力。

这些范围与 [Flutter 官方 Network View 文档](https://docs.flutter.dev/tools/devtools/network) 一致。

## 独立原型验证（2026-10-27）

`scripts/probe-devtools-network.dart` 只启动自建 loopback HTTP 服务与测试进程，不连接用户的业务 App。VM Service 保留认证，其地址不会写入原型缓存或输出。

在本机 Flutter 3.47.5 的 Dart 3.13.4 `dartvm` 中验证：

1. 调用扩展开启 HTTP profiling，发送测试 POST 请求。
2. 读取 HTTP 200 状态、请求正文和响应正文，校验测试内容。
3. 再发一个请求，使用前次 profile 的 `timestamp` 做 `updatedSince` 增量读取，确认出现新请求。
4. 写入 JSONL 缓存并读取校验，测试进程退出后文件仍存在。

输出摘要：`requestBodyVerified=true`、`responseBodyVerified=true`、`incrementalReadVerified=true`、`cachedRecords=2`。运行方式：

```sh
/path/to/dart-sdk/bin/dartvm scripts/probe-devtools-network.dart
```

缓存默认位于 `.build/devtools-network-probe/`。本机旧版定制 Dart 3.6.2 的命令行 VM 未提供可启动的 VM Service，因此该二进制未能完成原型；这不等于使用同版 Flutter 引擎的调试 App 不支持采集，实际接入时仍须按运行进程检测能力。

## 已接入的使用方式

在输出区域选择「网络」，勾选「网络采集」。开关按项目保存，默认关闭；支持任意项目类型，按当前运行进程的实际 VM 能力连接。也可在运行开始前，选中一条历史记录的网络页开启开关，供下次运行使用。无需安装额外 Dart SDK 才能运行 Runbar，采集器由 Swift 实现。

- 列表按请求开始时间从旧到新排列，最新在底部，显示毫秒时间、方法、地址、状态和耗时；可按方法、状态及内容组合筛选。完整历史连续滚动，无需翻页；滚动条对应全部匹配记录，可拖到任意位置，「最早 / 最新」直接跳转两端。后台按位置读取最多 256 条轻量摘要（不包含 Headers 或正文），窗口替换后释放旧摘要，只有可见行创建原生单元格。「跟随」默认开启，自动滚动到底部；向上滚动或拖动滚动条离开底部会关闭跟随，开关状态会保存。重新勾选后回到最新请求，不自动切换正在查看的响应。
- 「搜索全部内容」在 URL、请求/响应头、URL 查询参数及已缓存请求/响应正文中按关键词字面查找，不区分大小写。输入框选择「包含」或「排除」，回车或点 `+` 添加为标签，点标签的 `×` 删除。可用逗号、中文逗号、分号或换行一次添加多个词，空格保留为短语；每个范围的包含 / 排除各最多 16 个词，每词使用前 1024 个 Unicode 标量。未提交的输入同样参与即时筛选，提交为标签不会重新开始同条件的搜索。
- 点「筛选」分别设置 URL、请求/响应头、请求参数、响应内容。每组包含词可选择「全部满足 / 满足任一」，不同范围组之间仍为 AND；全部内容组的多个词允许分散命中不同范围。请求参数包含 URL 查询串及请求正文，支持 URL/form 百分号和加号解码。先取满足包含条件、方法、状态和 JSON 保留条件的结果，再剔除命中任一排除词或 JSON 排除条件的请求，排除优先，不受包含词的「全部 / 任一」设置影响。只设排除时从全部请求中剔除；未缓存、超限或已丢失的正文不能参与匹配，因此无法据此判断是否应排除。
- 网络筛选会自动记住最后使用的全部内容词、各字段包含 / 排除词、关键词全部 / 任一关系、JSON 条件、方法与状态。重启 Runbar 或切换运行记录后恢复，输入中的关键词恢复为标签；尚未点击「添加」的 JSON 编辑草稿不属于生效条件，不保存。仅保存条件，不保存额外的正文或调试地址。
- 搜索栏旁「方案」可为当前全部条件命名保存，所有项目和关联 App 共用；点击方案会替换当前条件，暂不叠加方案。重名保存更新原方案，垃圾桶删除方案但保留当前生效条件；「重置当前筛选」清空全部当前条件，已保存方案仍保留。最多 32 个方案，名称 1–80 个字符，全部设置最多 1 MiB。
- 「字段条件（JSON）」支持请求 / 响应正文的字段路径：`data.connectionid`、`$.data.connectionid`、`items[0].id`、`items[*].id`，含点的字段名可写 `["a.b"]`；仅支持这组路径语法，不执行脚本或表达式。添加条件时选择「保留 / 排除」和「等于 / 不等于 / 包含 / 不包含 / 存在 / 不存在」。保留条件需全部满足，排除条件任一命中即剔除；最多 16 条，每条路径 / 值各最多 1024 个 Unicode 标量，路径最多 64 段。
- JSON 数字 `1`、布尔值 `true`、`null` 与字符串区分；字符串可直接填文本，需要区分字符串数字时填 `"1"`，空字符串填 `""`。等于按标量值比较，字符串区分大小写；包含忽略大小写，可检查子对象的键和值。`[*]` 正向比较任一数组元素命中即可，否定比较表示所有元素均未命中。有效 JSON 中字段缺失时，「不等于 / 不包含 / 不存在」成立；非 JSON、正文未缓存或超限时不命中任何字段条件（会被保留条件过滤，但不会仅因此命中排除条件）。JSON 字段条件针对正文；URL 查询或 form 参数用请求参数关键词筛选。

  例如响应为 `{"reqtype":1,"status":0,"data":{"connectionid":1}}`：
  1. 只查看连接 ID 为 1：添加「保留 · 响应 JSON · data.connectionid · 等于 · 1」。
  2. 查看 reqtype 为 1，但不要连接 ID 为 1：添加「保留 · 响应 JSON · reqtype · 等于 · 1」和「排除 · 响应 JSON · data.connectionid · 等于 · 1」。
  3. 地址包含 `/dfc/`，排除 heartbeat 或 ping：URL 包含 `/dfc/`，全部内容排除 `heartbeat,ping`。
- 选中请求查看概览、Headers、Request、Response。宽面板左右分栏，较窄面板上下分栏；内容可选择、复制，并按 128 KiB 页面读取。四个标签均提供 JSON、XML、原始三种显示格式，默认 JSON，按标签分别记住选择；「自动换行」同样保存，关闭时长行横向滚动。切换请求、运行记录或重启 Runbar 不会重置偏好。无请求正文且 URL 包含查询参数时，Request 显示 URL 参数，保留重复名称和无值参数。概览、请求头和 URL 参数可显示为结构化 JSON/XML；请求/响应正文按原有格式解析，不覆盖原始文件。
- 格式化在后台完成，最多读取 1 MiB，输出最多 4 MiB，每次只返回一页。内容不符合所选格式时提示并展示原始内容，保留所选偏好，后续符合格式的请求仍自动格式化；原始回退内容同样可以翻页。空正文直接显示为空。JSON 保留正文中的字段顺序和数字原文，XML 保留 CDATA，不加载外部实体；含 DTD / 实体声明或非 UTF-8 的正文使用原始显示。
- 「暂停」仅暂停新增摘要，已记录的正文继续补齐，选中的请求优先加载；仍未结束的已知请求也按限量队列刷新完成状态，不拉入新请求。目标 VM 仍可能记录，继续后按增量游标补采可用数据。关闭项目开关停止读取，也不修改其他 DevTools 客户端的共享记录开关。
- 首次连接使用 VM 自己的时钟建立游标，并保留 1 秒重叠；从连接附近开始采集，避免拉取 VM 已保留的整份旧历史。请求身份由本次连接代次、isolate、请求 ID 组成，重叠读取更新同一条记录。VM 的 startTime 可能有毫秒抖动，因此优先以 PID 判断 VM 更换；isolate 身份区分热重启。
- 停止运行、切换连接与正常退出会取消并等待旧采集任务，再标记未完成正文并关闭数据库；历史网络数据随整条运行记录保留，也随运行记录一起移到废纸篓。历史 PID / 服务地址不会被用于自动重连。
- 使用 `--start-paused` 启动的程序可在开启采集后，点「恢复程序」继续执行。Runbar 不会自动改写已有运行命令，也不会未经操作恢复调试暂停。

网络页的「… → 清理目标采集缓冲」需要明确确认。这会影响同一个 VM 的 DevTools 记录，并使仍在进行中的请求停止记录；Runbar 本地缓存保留。没有后台自动清理或自动关闭共享 HTTP profiler。

## 本地存储与容量

每次运行的 `network/requests.sqlite` 保存摘要和正文缓存状态，`network/bodies/` 单独保存正文。完成请求由后台限量队列及时取回正文，无需先点开请求。尚未获取、响应进行中、进程已退出、格式不支持、超限和读写失败均有明确状态；未缓存时显示原因，只有已缓存的正文才显示字节数，不把缺失正文显示为成功缓存的空正文。旧缓存没有完整响应计时依据时，耗时显示未知，避免继续展示旧版的发送耗时。

同一数据库的后台采集、正文状态写入和界面查询共用按目录建立的读写协调器，整笔同步事务期间不会插入另一连接的界面查询；不同运行记录之间互不阻塞。协调器不跨网络请求、异步等待或正文格式化持锁，等待有超时且可取消。仍使用 DELETE journal，保持原数据库及回滚日志的容量策略，不引入持续增长的 WAL 文件。SQLite FULLMUTEX 继续保留，但不再把它误当成多连接之间的读写协调。

缓存忙（SQLITE_BUSY / SQLITE_LOCKED）和协调器短暂占用会进行最多 5 次可取消的退避重试，延迟依次为 100、200、400、800、1600 ms。重试前结束当前读连接或回滚失败事务，不积累查询结果和请求数组；采集游标只在摘要写入成功后推进。列表、选中请求正文及后台采集均按同一有界策略处理临时占用，持续失败才暂停并提示点击「继续」。空间不足、达到容量上限、只读、权限、文件损坏和 I/O 错误不会套用忙重试。

磁盘余量保护与 SQLite FULL 分开报告：前者显示当前可用量和所需余量，属于非重试型暂停，不伪装成 SQLite 13；后者保留真实错误码，并记录数据库实际字节数、可用磁盘字节数和显式设置的页数上限。SQLite 错误在回滚、关闭或 finalize 之前保存主错误码、扩展错误码和原始错误说明，界面据此区分原因，不再统一归为「磁盘空间与权限」。写入端在本次 `network/last-error.json` 覆盖保存最后一次错误（最多 4 KiB、权限 0600），不写 SQL 参数、请求/响应正文或 VM 地址；只读浏览不会写入诊断。自动回滚后的清理不覆盖最初的错误，重试成功也保留该诊断供排查。

正文筛选每批从 SQLite 读取最多 24 条候选元数据，释放源数据库锁后逐条以 64 KiB 块扫描正文，保留有上限的跨块重叠，不一次性加载整份历史正文。JSON 字段筛选只在需要时逐条读取最多 1 MiB 正文，先检查 UTF-8 和最多 128 层嵌套，再解析一次并复用同一对象判断该方向的所有条件；请求和响应对象分别释放，不保留跨记录对象图。每个后台时间片约 120 ms，结果未完成时显示「筛选中」并自动继续；取消页面读取不会让同条件的后台进度反复归零，切换条件或离开网络页面则取消旧任务。匹配 ID 与排序键存于私有 SQLite 临时库，页缓存 256 KiB、禁用内存映射，临时文件随实际磁盘余量增长，不再受 16 MiB 固定门槛限制；不复制正文到索引，也不在内存中保留全量 ID。临时库随连接关闭自动删除，参见 [SQLite 临时数据库说明](https://www.sqlite.org/c3ref/open.html)。

新建或写入的缓存带逐行变更序号，新增摘要、请求状态变化及正文保存后只重新检查发生变化的记录；未变化的重叠数据不会反复增加序号。变更序号、状态和摘要在同一 SQLite 事务中更新。旧版历史缓存使用只读全量初次扫描，不需要改写原数据库；源数据变化时重新建立结果。元数据查询、游标窗口和后台采集仍共用前述读写协调，正文扫描和格式化不持有源数据库锁。显示偏好保存格式与换行；网络筛选独立保存最后使用条件和命名方案，不增加正文副本。网络筛选保存到当前用户的本地设置，键为 `networkFilterPreferences`，输入变化延迟 350 ms 合并写入，离开面板时补存尚未写入的条件。设置体积、分组、关键词、JSON 条件和方案数量均受限，读取异常或保存失败显示明确提示，不覆盖原有方案后静默丢弃条件。

默认限制：

| 项目 | 上限 / 行为 |
| --- | --- |
| 摘要 | 默认完整保留，不设固定条数或 32 MiB 数据库上限；按实际磁盘余量增长，SQLite 页缓存仍为 1 MiB，关闭内存映射 |
| 请求 / 响应正文 | 每个方向各 1 MiB；超限保留摘要并标记正文未缓存 |
| 正文合计 | 默认按实际磁盘余量保留，不再因为累计 128 MiB 就遗漏后续正文；单个方向 1 MiB 的保护保留 |
| 磁盘保护 | 写入前保留 512 MiB 可用空间，并为当前批次 / 正文和临时事务文件预留余量；不足时在写入前暂停，释放空间后点击「继续」，不删除或淘汰历史 |
| 单次 VM 返回 | 8 MiB，按传输块检查并在 JSON 解码前中止超限响应 |
| 单批请求 | 2000 条，超限暂停接收并提示 |
| 并发 / 轮询 | 摘要约 1 秒刷新；正文每批最多 8 条，积压时连续补采，不再每批等待 1 秒；后台顺序取回并轮换 isolate，另有 1 个可取消的选中请求优先通道，同会话最多 2 个正文请求；界面更新合并至约 250 ms 一次 |
| 正文预览 | 每页 128 KiB；二进制仅显示本页前 4096 字节十六进制 |
| 格式化 | 单次后台读取最多 1 MiB，格式化结果最多 4 MiB，JSON 嵌套最多 128 层；每次只向界面返回一页，不保留多份格式化缓存 |

摘要窗口读取、筛选、数据库写入和正文读取均在后台 actor 中执行。滚动复用当前筛选的单份计数快照，采集更新或切换条件时重算；不积累历史窗口。选中行通过数据库读取完整元数据，不受当前摘要窗口替换影响。SQLite 内存页缓存为 1 MiB，正文不保存在列表数组中；保留量随上述窗口和返回上限受限。进程 RSS 仍包含 AppKit、JSON 对象和系统缓存，不承诺一个固定 RSS 数值。磁盘保留量与内存读取量独立控制。默认不自动淘汰历史，较长采集会持续占用磁盘，可通过删除不需要的运行记录回收。写入前的磁盘余量检查不能阻止其他进程同时占用空间；真正的文件系统配额、I/O 或空间分配失败仍会明确暂停，不盲目重试。显式 `NetworkLimits` 仍可为独立调用方设置条数、数据库页数和正文合计配额。

`updatedSince` 不是服务端分页，也不会清理目标 VM 自己保存的 profile；Runbar 的返回大小限制也不能限制目标 App 的 profiler 内存。长时间、大流量采集需要用户在适当时候清理目标采集缓冲。

只连接运行输出明确公告的回环地址，保留 VM 认证，不跟随重定向，不使用共享 Cookie / 响应缓存。网络目录为当前用户私有，数据库和正文文件权限为 0600。认证服务地址不额外写入网络数据库、请求身份、配置或错误信息；原始运行日志仍按原有规则保存终端输出，可能包含工具自行打印的服务地址。

## 32 MiB 容量问题

限制来源：本仓库提交 `d897f01191b124ab5d8dab43850056e3c2b6caec`，标题 `Add HTTP capture, global shortcuts and log workflow improvements`，Git Author / Committer 均为 `niesiyang`，时间 2026-10-27 10:54:43 +08:00。提交说明明确将 SQLite / 正文缓存设计为有界的磁盘保留量；它并不能作为内存控制的依据。

最初的网络采集实现将 `max_page_count=8192` 与 4096 B 页大小组合成 32 MiB 的磁盘硬上限，用于约束本地缓存保留量；它不是内存上限。请求头和索引较多时，约一万多条摘要就可能触发 SQLite 13，即使磁盘仍有大量空闲。默认写入连接改用 SQLite 引擎页数上限并保留独立 1 MiB 页缓存，既有数据库直接打开继续增长，不删除或重建旧文件；只读查看旧缓存不修改数据。默认记录条数、正文合计与临时匹配索引的固定总量门槛也同步解除，容量保护统一依据实际磁盘余量。参见 [SQLite max_page_count / cache_size](https://www.sqlite.org/pragma.html#pragma_max_page_count)。
